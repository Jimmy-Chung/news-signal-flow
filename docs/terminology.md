# 术语与命名改造方案

> 状态：**主词与品牌已定，P1 文案层已实施**（2026-11-17）。主词 = 节点，左上角品牌 = 热点观测台。数据层与代码标识符仍沿用 `entity`，见 §8 P3。
> 目标：把「实体 / 雷达 / 事件」这套从上游继承、或从知识图谱借来的词汇，换成和产品实际行为一致的「节点 / 进展 / 扩散 / 关注度」。

## 0. 结论先行

产品的真实动作是三步：**从热榜里抽出对象 → 持续观察这些对象 → 判断事情在往哪走**。
词汇应该只描述这三步，不该出现「实体」（信息抽取术语）、「雷达」（探测隐喻）、「投资者」（投研人格）。

推荐一套四个主词：

| 主词 | 指什么 | 替换掉 |
| --- | --- | --- |
| **节点** | 从新闻里抽出来、可以持续追踪的对象（公司/产品/人物/技术/政策/地点） | 实体 |
| **进展** | 这个节点上新发生的一件具体的事（语义去重后） | 事件、事件变化、新事实 |
| **扩散** | 有多少新来源开始跟进它 | 媒体扩散、新增媒体 |
| **关注度** | 综合热度（去重标题 + 来源 + 榜位 + 相关度） | 热度、强度 |

## 1. 先澄清一件事：代码里没有 Trader

对全部 tracked 文件做过不区分大小写的检索，`Trader` 只出现在 `README-EN.md`（从上游 TrendRadar 翻译来的受众描述："Traders/Investors"）。它没有进入任何代码、数据或界面。

但「投研口吻」确实还留在两个地方，比「实体」更隐蔽：

- `config/ai_analysis_prompt.txt:137` —— 要求模型按「投资者 / 品牌方 / 公众」三种角色给建议。这是把人预设成炒股和做营销的，和「观察事情如何发展」不是一回事。
- `web/scripts/suggest_interests.py:87` —— 提示词里写着「保留……自选股列表」。产品里并没有自选股。

这两处属于**人格层**的旧痕迹，建议和词汇一起改（见 §8 P4）。

如果你印象里还有一处明确的 Trader 概念，可能是在别的分支或早期版本里，告诉我位置我再核。

## 2. 真正的问题不是「实体」难听，是同一个概念有三四个名字

这是比换词更值得先解决的事。现状盘点：

| 概念 | 现在同时叫 | 出现位置 |
| --- | --- | --- |
| 被观察的对象 | 实体 / 节点 / ENTITY / 具体实体 / 活跃实体 / 全部实体 | `EntityRadar.tsx:484`（同一句里「实体关系图：节点可拖拽」）、`:1382`、`:1395`、`:1396` |
| 一根连线 | 实体关系 / 互联关系 / 关系图 | `:1383`、`:1396`、`:484` |
| 3 小时切片 | 时间帧 / 帧 | `:563`、`:597` |
| 一轮生成的完整结果 | 实体快照 | `:1479`、`:1481`、`:1546` |
| 一件新发生的事 | 事件 / 事件变化 / 事件变化速度 / 新事实 | `:1256`、`:307`、`:484`、`:501`、`:598` |
| 新来源跟进 | 媒体扩散 / 媒体扩散速度 / 新增媒体 / 新增来源 | `:307`、`:484`、`:502`、`:598`、`:506` |
| 受关注程度 | 热度 / 强度 / 关注热度 | `:284`、`:499`、`:623`、`:1246` |

同一句里「实体」和「节点」并用，同一个指标在卡片、图例、悬浮提示里叫三个名字——这是用户真正会困惑的地方。**只把「实体」替换成「节点」，问题只解决一半。**

## 3. 三条命名原则

1. **一个概念一个词。** 代码里可以有别名，界面上不能有。
2. **名词描述「用户在观察什么」，不描述「技术上怎么实现」。** 实体是 NER/知识图谱的术语，快照是存储的术语，都不该出现在用户面前。
3. **新词要接得住项目名。** 项目叫 News Signal Flow，主词就该落在「信号 / 流 / 发展 / 观察」这条线上，而不是「雷达 / 交易」这条线。

## 4. 推荐词汇表

### 4.1 四层本体

```
报道 ──抽取──> 节点 ──观察──> 进展（发生了什么）
                │            扩散（谁在跟进）
                └──────────> 关注度（有多受关注）
```

- **报道**：一条原始新闻，界面上统一叫「报道」，保留「线索」作为"被兴趣筛中的报道"的称呼（这个词很有辨识度，不要丢）。
- **节点**：长期存在的被观察者。
- **进展**：节点上新增的、去重后的一件具体事。注意不要叫「事实」——模型只能观察到"被报道的进展"，叫事实是过度断言，和 README 里"模型可能误判，请核对原文"的定位自相矛盾。
- **扩散**：传播层的唯一指标。
- **关注度**：综合热度。

## 5. 主词的三个候选

| 主词 | 优点 | 风险 | 适合 |
| --- | --- | --- | --- |
| **节点**（推荐） | 你本来就这么叫；图谱原生；两个字，界面好排 | 离开图谱语境略抽象，偏技术 | 自用 / 技术型用户 |
| 关注对象 | 最口语，无歧义 | 四个字，卡片和标签里很挤；代码里 `object` 太泛 | 面向非技术用户 |
| 议题 | 舆情监测行业惯用语 | 装不下「英伟达」「雷军」这类具体对象；且会和数据里的「话题」撞车 | 舆论监测场景 |

**已定：界面统一用「节点」，在首次使用/空态的说明性长句里用「关注对象」解释一次**，例如"每个节点是一个你正在观察的对象"。不要两种词并列出现在标签上。

## 8. 分四步落地

| 阶段 | 改什么 | 风险 | 验收 |
| --- | --- | --- | --- |
| **P1 文案层** | 只改中文串、aria-label、`<title>`、测试断言 | 低，可独立发布 | `grep -rn "实体\|雷达" web/app` 只剩代码标识符；`npm test` 通过 |
| **P2 路由与品牌** | `/entities` → `/nodes`；`/api/local-admin/entities` → `/nodes`（旧路径留别名）；品牌名 | 中，外部书签会断，需别名 | 旧 URL 仍可取到数据 |
| **P3 代码与数据** | 类型、字段、文件名、ID 前缀、CSS、导出脚本 | 中高，跨 6 个测试 + Inbox 存储 | 重新生成一次快照，页面与旧数据都不报错 |
| **P4 文档与人格** | `README.md`、`web/README.md`、抽取提示词、兴趣助手提示词、MCP 文案 | 低 | 全仓库不再出现「实体/雷达/自选股/投资者」 |

几个容易踩的坑：

- `web/tests/rendered-html.test.mjs:53-66` 直接断言了「实体雷达」「实体快照」「实体类型着色」等文案，P1 必须同批改测试，否则一改就红。
- `entity-extractions.json` 是 LLM 结果缓存，改名不要重新生成。
- Inbox 的 `entityName` 是用户历史数据，改字段名要么读时兼容，要么写一次性迁移，别直接丢弃。

## 9. 顺手清掉的遗留

1. `web/app/EventRadar.tsx` 没有任何引用，是「事件」这套旧概念的残骸，删掉。
2. `web/app/interests/page.tsx` 只是 redirect 到 `/entities`；`/` 和 `/entities` 渲染的是同一个 view，路由可以收敛成一个。
3. `TrendRadar` 字样还在界面、日志、通知标题里外泄（`layout.tsx`、`run-trendradar.sh`、多处 notification）。品牌换名后这些会显得没做完。
4. 环境变量 `TREND_RADAR_*` 是部署契约，**不要跟着改**，否则老部署全挂；只在文档里说明"变量名保留历史原因"。
5. `config/ai_analysis_prompt.txt` 的「投资者 / 品牌方 / 公众」建议换成和"判断事情发展"匹配的三问：下一步看什么 / 什么会证伪 / 谁在跟进。
